# Code of conduct

SpaceSharp is a small open-source project, and the places where people meet around it (issues, pull requests, discussions, reviews) should be worth showing up to. This page says what that means, what it asks of the maintainer in return, and what happens when it doesn't hold.

## What we expect

- **Be kind and be direct.** Disagree with ideas, not with people. "This approach will break on exFAT because…" is welcome; "this is stupid" is not.
- **Assume good intent, and ask before you conclude.** Most friction in a project like this is a misunderstanding about what someone meant or tried. A question costs less than an accusation.
- **Help newcomers.** Explain the thing, link the file, say which command to run. Nobody is expected to know the codebase, Velopack or the NTFS record format before they can ask a question, and "read the docs" is not an answer unless it comes with which doc and which section.
- **Keep it about the project.** Politics, religion and other people's personal lives are not topics here, however interesting they are elsewhere.
- **Respect time and effort.** A pull request that is declined still deserves a reason; a review that asks for changes still deserves a thank you; a bug report that turns out to be user error still deserves a pointer to the right setting.
- **Write so others can follow.** Issues and pull requests are in English so everyone can read them. Norwegian is fine in a private message to the maintainer, and translation questions can quote the language concerned.
- **Say what you used.** If a contribution was written with help from an AI tool, say so in the pull request. That is not a mark against it; it tells the reviewer where to look harder, and it keeps the project honest about where its code comes from. You are responsible for what you submit, whoever or whatever drafted it.

## What we don't accept

- Insults, slurs, harassment or threats, in any channel connected to the project.
- Sexualized language or imagery, or unwelcome attention of any kind.
- Publishing someone's private information, such as a real name, address, employer or photographs, without their permission.
- Sustained disruption: derailing threads, reopening settled decisions to wear people down, flooding the tracker with duplicates, or following people to other spaces to continue an argument.
- Passing off someone else's work as your own, including code copied without its license.
- Anything that would reasonably be considered unacceptable in a professional setting.

## What you can expect from the maintainer

- An answer to an issue or pull request within a week, even if the answer is "not yet" or "no".
- A reason with every "no", and a pointer to what would change it if anything would.
- Decisions explained in the thread where they are made, so they can be found later, rather than in private.
- Credit in the changelog for contributions that ship, under the name you use on GitHub unless you ask for something else.
- The same rules applied to the maintainer as to everyone else. If the maintainer slips, say so; the private channel below works in both directions.

## Scope

This applies to the GitHub repository (issues, pull requests, discussions, wiki, releases), to the project website, and to anywhere someone represents the project, such as a talk, a post or a package listing that speaks for SpaceSharp. It also applies when project spaces are used to target someone who is not a participant, and to conduct outside the project when it is directed at a participant because of their participation.

## Reporting

If you see or experience something that does not belong here, report it to the maintainer privately through GitHub: open the maintainer's profile at [github.com/ClearanceClarence](https://github.com/ClearanceClarence) and use the contact listed there. For anything that is also a security matter, follow [SECURITY.md](SECURITY.md).

Say what happened, where, and when, and include links or screenshots if you have them. Reports are read by the maintainer only, handled as quickly as possible, normally within a few days, and kept confidential as far as the situation allows; the person reported is not told who reported them unless you agree to that. You will get a reply, and if a report is about the maintainer, say so and it will be taken as seriously as any other, though in a one-person project there is nobody else to hand it to.

Reporting in good faith is never held against anyone, even when the report turns out to be unfounded. Knowingly false reports are themselves a violation.

## What happens next

The maintainer decides the response, in proportion to what happened and whether it has happened before:

1. **A private word.** For a first slip or a borderline case: an explanation of what crossed the line and why, with no public record.
2. **A public correction.** For a clear violation in a thread: a note in the thread, and removal or editing of the offending content. The edit is marked as the maintainer's.
3. **A temporary block.** For repeated behavior after a warning: no interaction with the repository for a set period, stated when the block is made (usually 30 days).
4. **A permanent block.** For harassment, threats, doxxing, or a pattern that does not stop.

Content is removed only as far as needed; a thread is not deleted because one message in it crossed a line. Blocks use GitHub's own tools and are recorded in a private note so the maintainer can be consistent over time.

Someone who disagrees with a decision can say so in the same private channel; the maintainer will read it and answer, though there is no formal appeals process in a one-person project. A permanent block can be revisited after a year on request.

## Changes to this document

Changes are made by pull request like anything else, with the reason in the commit message, so the history shows what changed and why. The version in the main branch is the one that applies.
